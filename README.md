# ONTOFLOW — HVAC Knowledge System

온톨로지 기반 건물 지식 탐색 페이지. 2026년 제14회 HVAC 경진대회 §5 활용 사례용.

```
작업/
├─ index.html               페이지 골격 · 정적 문구(KO/EN 두 언어가 모두 마크업에 있음)
├─ css/style.css            디자인 시스템 전체
├─ js/data.js               연구 데이터 — 이 파일만 고치면 화면이 따라온다
├─ js/app.js                화면 코드 — KB 객체의 모양만 알고 출처는 모른다
├─ js/graph-data.js         온톨로지 부분 그래프(노드 484 · 엣지 832) + 굳은 좌표
├─ js/graph.js              그래프 렌더러 — canvas 2D, 외부 라이브러리 없음
├─ tools/extract_graph.py   graph-data.js 를 ontology.ttl 에서 다시 만드는 스크립트
├─ tools/build_fonts.py     fonts/ 를 만드는 스크립트 (문구를 고치면 다시 돌린다)
└─ tools/make_qr.py         배포 URL 로 포스터용 QR 을 만드는 스크립트
```

## 실행

```bash
cd 작업
python -m http.server 8000     # http://localhost:8000
```

`index.html` 을 브라우저에서 바로 열어도 된다 — `fetch` 를 쓰지 않으므로 `file://`
에서도 전부 동작한다. 모든 경로가 상대경로이므로 폴더째 어디에 올려도 그대로 돈다.

## 서체

한글은 **Apple SD Gothic Neo**, 라틴·숫자는 **IBM Plex Mono**. 둘 다 `fonts/` 에서
직접 불러오므로 외부 요청이 0건이다.

`tools/build_fonts.py` 가 만든다. 이 장치에 설치된 원본을 읽는다
(`%LOCALAPPDATA%\Microsoft\Windows\Fonts`).

| 파일 | 굵기 | 쓰는 자리 | 크기 |
| --- | --- | --- | --- |
| `applesd-500.woff2` | 500 | 본문 | 약 35 KB |
| `applesd-700.woff2` | 700 | 강조 · 제목 | 약 35 KB |
| `applesd-800.woff2` | 800 | 큰 제목 | 약 36 KB |
| `plex-mono-{300,400,500,600}.woff2` | — | 숫자 · URI · 라벨 | 각 약 15 KB |

합계 약 165 KB. 원본이 각 3.8 MB 이므로 이 페이지가 쓰는 글자만 남긴 것이다.

**화면 문구에 새 한글을 넣으면 스크립트를 다시 돌려야 한다.** 서브셋에 없는 글자는
시스템 서체로 떨어진다. 스크립트가 끝에 빠진 글자를 검사해 알려 준다.

```bash
cd 작업
python tools/build_fonts.py
```

### 원본 다섯 벌이 한 패밀리가 아니다

`AppleSDGothicNeoL/M/B/EB/H.ttf` 다섯 파일 모두 `usWeightClass` 가 **400** 이고
패밀리 이름이 서로 다르다(`AppleSDGothicNeoM00`, `AppleSDGothicNeoB00` …).
운영체제가 굵기로 묶어 주지 않으므로, `@font-face` 에서 굵기를 직접 지정해
같은 `font-family` 로 묶었다. L(300)과 H(900)은 화면에서 쓰지 않아 뺐다.

### 두 서체를 겹쳐 두는 이유

`--kr` 스택이 `'Apple SD Gothic Neo', 'IBM Plex Mono', …` 인 것은 오타가 아니다.

| 글자 | Apple SD | Plex Mono |
| --- | --- | --- |
| `·` `−` `•` | 없음 | 있음 |
| `→` `≠` `≈` | 있음 | 없음 |

서체 대체는 **글자 단위**로 일어나므로 두 벌을 겹쳐 두면 서로 빈 자리를 메운다.
이 페이지는 `·` 를 구분자로 아주 많이 쓰는데, 이 순서가 아니면 그 점만
시스템 서체로 떨어져 리듬이 어긋난다. `build_fonts.py` 의 빠진 글자 검사도
한 서체가 아니라 **두 서체의 합집합**으로 한다 — 한쪽만 보면 헛경고가 난다.

## 질의응답 루프 (03)

세 문항이 무한히 반복된다. 진행은 `레퍼런스/t-ranno`(bistskku.com/projects/t-ranno)의
방식을 따랐다.

```
질문 타이핑(캐럿 깜빡임)
  → 그래프 눌림 + 답이 되는 노드 점등
  → 노드가 왼쪽 답변 슬롯으로 비행
  → 근거 · 출처 · 검증 상태 채움
  → 리셋 → 다음 문항
```

`IntersectionObserver` 로 이 파트가 화면에 들어올 때 시작하고, 벗어나면 멈춘다.

### 답을 손으로 적어 두지 않는다

`js/app.js` 의 `qaResolve()` 가 `GRAPH` 를 실제로 걸어서 답이 되는 노드를 찾는다.
손으로 적어 두면 그래프를 다시 뽑았을 때 조용히 낡기 때문이다.

| 문항 | 어떻게 찾나 | 실제로 나온 답 |
| --- | --- | --- |
| 풍량 7,300 의 출처 | ZHUA01 → `hasQuantityValue` → 값 7,300 → `sourcedFrom` | 계산서 p.252 · p.253 |
| ZHUA01 부품 구성 | ZHUA01 → `brick:hasPart` | A_H_Coil · Cool_g_Coil · ZHUA01_MOT · ZHUA01_SF |
| 정격 vs 계산 | 값 상태가 `DIVERGENT` 인 값 노드 | 68개 중 앞 5개 |

부품 구성의 답은 질문·정답 카탈로그의 D1 정답과 정확히 같다.

### 노드를 어떻게 날리나

노드는 `<canvas>` 안에 있어 CSS 로 움직일 수 없다. 그래서 노드의 화면 좌표
(`graph.js` 의 `screenPos(i)`)에 DOM 조각(`.qa2-chip`)을 하나 만들어 겹쳐 놓고,
목표 슬롯까지의 차이만큼 `transform` 으로 옮긴다. 레퍼런스의 `flyTo` 와 같은 방법이다.

**좌표를 `requestAnimationFrame` 안에서 재면 안 된다.** 처음에 그렇게 짰는데,
프레임이 굶는 상황(백그라운드 탭 · 인쇄 · 헤드리스 캡처)에서는 콜백이 오지 않아
**답변이 영구히 비어 있었다.** `getBoundingClientRect()` 를 부르면 그 자리에서
레이아웃이 계산되므로 방금 붙인 조각의 크기도 이미 정확하다 — rAF 가 필요 없었다.

### 챗봇이 아니다

말풍선 · 아바타 · 입력창 · 발화자 표시를 쓰지 않는다. 왼쪽은 `질문 / 사람이 입력한
문장` 과 `온톨로지 기반 답변 / 지어낸 문장이 아니라 그래프에서 직접 조회한 값입니다`
두 덩어리로 갈라 두고, 답변만 다른 면(`--panel`)에 올려 '돌려받은 기록' 으로 보이게 했다.

## 등장 연출과 파트 전환

두 가지가 함께 돈다.

**파트 전환은 스크롤에 묶여 있다.** `--enter` 를 스크롤 위치에서 계산해 넣고, CSS 는
그 값을 위치와 불투명도로 옮기기만 한다. `transition` 을 걸지 않는 것이 중요하다 —
걸면 보간이 끼어들어 손과 화면이 어긋난다. 스크롤을 멈추면 움직임도 멈추고,
되감으면 되감긴다. 처음에는 CSS 전환 한 번으로 처리했는데, 섹션이 들어온 순간
0.7초 재생되고 끝나서 아무리 천천히 스크롤해도 '넘어간다'는 감각이 없었다.

움직이는 것은 본문 칸뿐이다. 섹션 제목(`.sec-label`)은 `sticky` 로 붙어 있는 쪽이라
건드리지 않는다 — `transform` 을 `sticky` 의 조상에 걸면 붙어 있는 성질이 깨진다.
질의응답의 그래프 판도 뺀다(캔버스를 옮기면 비행 좌표가 어긋난다).

**항목 등장**은 도시공원 레퍼런스의 방식을 그대로 쓴다 — `--ox`/`--oy` 로 제자리
바깥에 두고 `--o` 순서로 불러들이며, 곡선도 저쪽 것(`cubic-bezier(.18,.84,.26,1)`,
1.15초)이다. 반복 항목(표 · 목록 · 격자)이 있으면 블록 대신 항목을 하나씩 올린다.

히어로는 둘 다의 대상이 아니다 — 첫 화면은 포스터 스크린샷으로 쓰이므로
스크롤하지 않은 그 상태에서 이미 완성돼 있어야 한다.

### 숨김 규칙을 JS 가 켠다

`html.reveal` / `html.parts` 클래스는 JS 가 붙인다. 이 연출은 본문을 기본적으로
투명하게 만드는 장치이므로, 스크립트가 실패했을 때 숨김만 남으면 페이지 전체가
빈 화면이 된다. 클래스를 JS 가 붙이면 스크립트가 죽어도 아무것도 숨지 않는다.

거기에 **시간 안전망**을 하나 더 뒀다. `IntersectionObserver` 의 콜백은 '렌더 갱신
뒤'에 오는데, 프레임을 아껴 주는 상황에서는 그 갱신이 오지 않아 콜백도 오지 않는다.
실제로 헤드리스 스크린샷에서 히어로 아래 전체가 빈 화면(표준편차 0.00)으로 찍혔다.
2.4초 뒤에는 조건 없이 연다. `@media print` 에서도 숨김을 해제한다.

## 실제 기능과 정적 데이터의 구분

브라우저에서 실제로 도는 것과 미리 계산해 둔 것을 섞어 놓지 않았다.

| 실제로 도는 것 | 미리 계산해 둔 것 |
| --- | --- |
| 그래프 렌더링 · 회전 · 2D↔3D 모프 | 노드 484개의 2D·3D 좌표 (`tools/extract_graph.py`) |
| 노드 hover 판독 · 관계 묶기 | 그래프에 담을 부분집합(설비 47대를 씨앗으로) |
| 질의응답의 답 찾기(`qaResolve()` 가 `GRAPH` 를 걷는다) | 질문 문장과 읽는 법 |
| 언어 전환 · 파트 전환 · 등장 연출 | 규모 지표 · 값 상태 분포 · 파이프라인 설명 |

**업로드 기능은 없다.** 실제 구축은 별도 파이프라인에서 87분 28초 · \$24.19 에
수행되었고, 이 페이지는 그 산출물인 `ontology.ttl` 을 읽어 만든 탐색 화면이다.
동작하지 않는 업로드 버튼을 두어 되는 척하지 않았다.

**SPARQL 엔진도 브라우저에 없다.** 질의응답의 답은 미리 뽑아 둔 부분 그래프
(`js/graph-data.js`)를 JS 가 걸어서 찾은 것이다. 화면에 `SPARQL 직접 실행` 이라고
적힌 것은 카탈로그의 정답이 사람이 쓴 SPARQL 로 뽑혔다는 뜻이고, 이 페이지가
그 자리에서 SPARQL 을 돌린다는 뜻이 아니다.

55,714 로 박히기 때문이다(실제로 그렇게 찍혔다). 화면에 보이는 숫자는 언제나 최종값이다.

### 헤드리스로 검증할 때의 함정

`--screenshot` 으로 이 페이지를 확인할 때 헛다리를 여러 번 짚었다. 남겨 둔다.

- **rAF · IntersectionObserver · CSS 트랜지션이 진행되지 않는다.** 가상시간에서는
  프레임이 거의 돌지 않아 전부 초기 상태에 얼어붙는다. 등장 연출과 카드 페이드가
  투명한 채로 찍힌다.
- **`load` 이후에 JS 가 만든 DOM 은 캡처에 잡히지 않는다.** 확인용으로 넣은
  고정 위치 마젠타 상자조차 찍히지 않았다. 반면 스크립트 최초 실행 중에 그린 것
  (KPI 숫자 · 카드 · 그래프)은 정상적으로 찍힌다.
- **창 최소 폭이 강제된다.** `--window-size=390,3000` 을 줘도 실제
  `clientWidth` 는 489 였다. 390px 이미지에 489px 레이아웃이 잘려 담기므로
  글이 잘린 것처럼 보인다 — 레이아웃 문제가 아니다.

  대신 **폭을 못박은 iframe** 으로 확인한다. 임시 페이지에 `<iframe width="390"
  height="844" src="index.html">` 를 두면 그 안은 진짜 390px 뷰포트가 된다 —
  미디어쿼리·`vh`·sticky 가 모두 그 폭과 높이를 기준으로 동작한다. 부모에서
  `f.contentWindow` 로 스크롤시키고 `f.contentDocument` 로 재면 된다.
  `--allow-file-access-from-files` 가 있어야 `file://` iframe 에 접근할 수 있다.
  스크린샷도 이 방법으로 찍으면 핸드폰 폭의 실제 픽셀이 나온다.
- **커서 없는 기기를 흉내낼 수 있다.**
  `--blink-settings=primaryHoverType=1,availableHoverTypes=1,primaryPointerType=2,availablePointerTypes=2`
  를 주면 `(hover: none)` 과 `(pointer: coarse)` 가 참이 된다. 손가락용 문구와
  `@media (hover: none)` 규칙을 그대로 확인할 수 있다.
- **터치는 합성 이벤트로 확인한다.** `new PointerEvent('pointerdown', {pointerType:
  'touch', ...})` 를 `pointerdown → pointerup → pointerout → pointerleave → click`
  순으로 보낸다. 실제 순서가 이것이고, 이 순서 때문에 생기는 버그가 있다(아래).
- **`scroll-behavior: smooth` 는 완료되지 않는다.** 스크롤시켜 찍으려면
  `document.documentElement.style.scrollBehavior = 'auto'` 를 먼저 준다.
- **오류 훅을 `iframe.onload` 에서 붙으면 로드 시점 오류를 놓친다.** 스크립트는
  이미 다 돌았기 때문이다. 실제로 app.js 가 `SyntaxError` 로 통째로 죽었는데
  점검 결과는 "오류 0" 이었고, 화면만 이상했다. 오류를 보려면 임시 사본의
  `<head>` 맨 앞에 `window.addEventListener('error', ...)` 를 넣어 두고 읽는다.
  `file://` 은 기본적으로 교차 출처라 메시지가 `Script error.` 로만 오므로
  `--allow-file-access-from-files` 가 함께 필요하다.
- **JS 문자열 안에 진짜 줄바꿈이 들어가면 파일 하나가 통째로 죽는다.** 파이썬
  힙독으로 JS 를 쓸 때 `
` 이 실제 줄바꿈으로 풀려 이 일이 났다. 여러 줄
  문자열은 배열에 담아 `join(String.fromCharCode(10))` 로 잇는 편이 안전하다.
- **스크롤 이벤트는 프레임마다 하나로 합쳐진다.** 가상시간에서는 프레임이
  드물어서, 0.26초마다 `scrollBy` 를 열다섯 번 해도 이벤트는 여섯 번만 온다.
  그래서 스크롤로 움직이는 상태 기계가 "멈춰 있는 것처럼" 보인다 — 실제로
  이것 때문에 사이트에 없는 버그를 두 번 쫓았다. 스크롤 사이에 프레임 한 번
  분량(2초쯤)을 주거나, `resize` 를 합성해서 같은 함수를 직접 불러 비교한다.

03 질의응답처럼 시간에 따라 진행되는 부분은, 임시 사본에서 `IntersectionObserver`
게이트를 직접 호출로 바꿔 인라인한 뒤 가상시간을 늘려 가며 DOM 을 덤프하는 편이
확실하다. 실제로 그 방법으로 문항별 답(계산서 p.252 · p.253 / 부품 4개)을 확인했다.
파트 전환과 등장 연출은 인라인 스타일로 꺼 두어야 색이 제대로 찍힌다.

## 핸드폰에서 보는 화면

포스터의 QR 로 들어오는 사람은 대부분 손에 들고 본다. 넓은 화면에서만 맞춰 두면
여기서 무너진다. 실측으로 잡은 것들을 남긴다.

**그래프 띠는 상단 바 높이에 붙는다.** 좁은 화면(1079px 이하)에서 그래프는
화면 위쪽에 sticky 로 붙고 내용이 그 아래로 흐른다. 그런데 상단 바는 780px
이하에서 두 줄이 되어 **105px** 이 되는데 띠는 `top: 56px` 에 못박혀 있었다 —
띠의 조작 줄(46px) 이 바 뒤로 완전히 숨었다. 지금은 `--top-h` 한 곳에서 정하고,
`app.js` 의 `topHeight()` 가 `ResizeObserver` 로 실제 높이를 재서 덮는다.
언어를 바꾸면 링크 길이가 달라져 줄 수가 바뀌므로 `register()` 로도 건다.

**띠 높이는 `svh` 로 잡는다.** `vh` 는 아이폰 사파리에서 '주소창이 숨은 상태'
높이다. 주소창이 보이는 동안 실제로 보이는 높이는 그보다 작아서, `42vh` 가
화면의 절반 가까이를 먹는다. `dvh` 는 쓰지 않았다 — 스크롤 중에 값이 변하면
캔버스가 다시 잡혀 그래프 배율이 흔들린다. `svh` 는 변하지 않으면서 안전하다.

**파트를 고르는 결정선을 띠 아래로 내렸다.** `vh * 0.42` 는 넓은 화면에서는
문제가 없다(띠가 오른쪽 칸이다). 좁은 화면에서는 그 선이 띠 뒤에 숨어서, 아직
보이지도 않는 파트가 '지금 보는 것' 이 됐다 — `#explore` 로 스크롤해도 상태가
생성 중에 머물러 노드를 눌러도 판독이 뜨지 않았다. `decideLine()` 이 띠가 위쪽에
붙어 있을 때만 선을 띠 아래(+44px)로 내린다. 파트 전환과 문항 전환이 같은 선을 쓴다.

**01 무대는 위아래로 쌓는다.** 두 칸을 유지하면 단계 칸이 181px 이고, 두 열로
접으면 한 열이 71px 이다. `hvo:hasQuantityValue`(11px 모노로 139px)가
`hvo:hasQua…` 로 잘렸다. 쌓으면 단계 칸이 화면 폭을 다 써서 술어 이름이 온전히
들어간다. 클래스 이름은 최대 191px 이므로 TBox 는 한 열로 둔다.
단계 높이는 `min-content` — `auto` 로 두면 가장 큰 단계에 셋 다 맞춰져
213px × 3 = 643px 이 된다.

**손가락에는 커서 규칙을 쓸 수 없다.** 탭 한 번에 `pointerdown → pointerup →
pointerout → pointerleave → click` 이 온다. `pointerleave` 에서 hover 를 지우던
코드 때문에 판독이 뜨자마자 사라졌고, 02 파트가 아무것도 하지 않는 칸이 되어
있었다. 지금은 마지막 입력이 손가락인지 기억해서

- `pointermove` 는 터치에서 무시한다 (누른 채 끄는 것은 스크롤이다)
- `pointerleave` 로 지우지 않는다 — 고른 노드가 다음 탭까지 남는다
- `click` 에서 좌표로 다시 집는다 (`pointerleave` 가 이미 지나갔으므로)
- 집는 반경을 18 → 28px 로 넓힌다 (손끝은 커서만큼 정확하지 않다)
- 빈 곳을 탭하면 닫힌다 — 닫는 방법이 있어야 한다

안내 문구도 `fine()` 으로 갈라 쓴다. "커서를 올려 보세요" 는 손에 들고 보는
사람에게는 거짓말이다.

**날아간 조각을 치운다.** 조각·실·표식을 지우는 일이 `later()` 타이머 안에 있어서,
문항을 중간에 넘기면 `qaClearFor()` 가 그 타이머까지 취소했다 — 지우는 일 자체가
사라져 문항 세 개를 훑는 동안 15개가 화면에 쌓였다. `qaReset()` 과 `qaStop()` 이
`qaFlyClear()` 로 비행층을 비운다.

**문항 칸은 띠 아래에 보이는 만큼.** 넓은 화면의 `74vh` 를 그대로 쓰면 내용
아래로 200px 넘는 빈 자리가 남아 띠 아래가 텅 빈 것처럼 보인다.
`calc(100svh - var(--top-h) - min(46svh, 330px) - 26px)` 로 한 화면에 한 문항.

**가로로 누우면 그래프를 옆 칸으로 세운다.** 세로는 높이가 없고 가로는 폭이
있다. 844x390 에서 위쪽 띠로 두면 상단 바 57 + 띠 148 을 뺀 137px 만 남는다.
그래서 `(orientation: landscape) and (max-height: 600px) and (min-width: 620px)`
에서는 넓은 화면과 같은 배치로 바꾼다 — 그래프 오른쪽 칸(844 기준 340x311),
내용 왼쪽(412px). 상단 바도 한 줄로 되돌린다(620~780px 구간에서 두 줄 105px 은
360px 높이의 29% 다). 세로에서 한 화면씩 주던 `min-height` 도 가로에서는 뗀다.

**'위쪽 띠인지' 는 화면 폭이 아니라 배치가 말해 준다.** `decideLine()` 이
처음에는 `max-width: 1079px` 이면 띠라고 보고 판정선을 띠 아래로 내렸다.
누운 핸드폰은 폭이 좁아도 그래프가 옆 칸인데, 그것까지 띠로 취급해서 390px
높이에서 선이 335px 에 놓였다 — 파트가 화면 거의 바닥에 닿아야 바뀌고,
그래서 02 를 잠긴 채로 지나갔다. 지금은 띠 폭이 칸 폭의 80% 를 넘는지로
판단한다. 세로는 333/335, 가로는 340/772 다.

**생성이 02 에 도착하기 전에 끝나야 한다.** 그러지 않으면 그래프 위에
"잠시 후 사용할 수 있습니다" 가 떠 있고 02·03 이 흐린 채로 남는다 — 실측으로
390x844 에서 페이지 88% 까지 그 상태였고, 고장난 것처럼 보인다. 세 가지를 걸었다.

- 시작을 앞당긴다 — 좁은 화면에서는 무대가 **두 화면 반** 앞에 왔을 때 시작한다
  (넓은 화면은 한 화면). 세로에서는 사실상 열자마자, 가로에서는 조금 내리면 시작된다.
- 길이를 줄인다 — 좁은 화면에서는 11초 대신 **7초**. 문서가 화면 높이의 여섯
  배라서 같은 11초로는 02 까지 못 끝낸다.
- 그래도 01 을 지나쳤으면 남은 것을 **2.2초** 에 나눠 끝낸다(`ingUrge()`).
  즉시 채우면 결과가 짠 하고 나타나므로, 자라는 것이 보이는 만큼은 남긴다.
  진행률이 튀지 않게 지금 값을 유지하면서 전체 길이만 줄인다.

`apply()` 에서 조건 없이 `ingPlay()` 를 부르던 것도 없앴다. 첫 프레임에 STATE 가
`''` -> `'build'` 로 바뀌면서 **페이지를 열자마자** 시작되어, 핸드폰에서는 히어로를
보는 동안 보이지 않는 곳에서 다 만들어졌다. 시작 조건은 `ingEarly()` 한 곳에만 둔다.

**스크롤 처리를 rAF 에 맡기지 않는다.** 네 곳이 모두 플래그를 세우고 rAF 안에서
일하고 플래그를 내리는 모양이었다. rAF 콜백이 한 번이라도 오지 않으면 플래그가
선 채로 남아 그 시스템은 스크롤에 **영구히** 반응하지 않는다. graph.js 가 이미
이 함정에 빠져 "어디로 스크롤해도 캔버스가 빈 화면" 이 됐던 그 구조다.
하는 일은 rect 몇 번 읽고 클래스를 토글하는 정도이므로 그 자리에서 바로 한다
(`onScroll()`).

**질의응답은 03 에 와 있을 때만 돈다.** `qaSync()` 에 그 검사가 없었다.
이 함수는 스크롤마다 불리고 고르는 값이 기본 0 이므로, 온톨로지가 다 만들어지는
순간 **어디에 있든** 1번 문항이 시작됐다 — 01 을 보고 있는데 그래프에서 답변판으로
선이 그어지고 질문이 타이핑됐다. 실측 로그에도 build 파트에서
`qa=[running,idle,idle]` 로 찍혀 있었는데 그때는 넘겼다. 지금은 `STATE !== 'qa'`
면 바로 돌아온다. 확인: 03 밖에서 질의응답 흔적 0(세로 · 가로 · 넓은 화면).

**문서가 온톨로지가 되는 것을 실제로 잇는다.** 예전에는 왼쪽에서 종이가 흘러가고
오른쪽에서 그래프가 자라는 두 장면이 서로 무관하게 돌았다. 시트는 자기 칸
오른쪽 끝(88%)에서 옅어져 사라지고 거기서 끝이었다 — 무엇이 무엇이 되는지
화면이 말해 주지 않았다("걍 따로 논다").

이제 그 사라지던 자리에서 이어받아, 지금 켜져 있는 단계(TBox·RBox·ABox)를
한 번 거쳐, **방금 만들어진 노드** 자리로 들어가고 그 자리에 고리가 한 번 퍼진다.
도착 지점은 지어낸 좌표가 아니라 `G.screenPos()` 로 얻은 실제 노드 위치다 —
`buildRank` 의 역표를 만들어 "지금 순위 n 인 노드가 누구인가" 를 찾는다.
시트가 1.1초 간격(`--d` 0.0/1.1/2.2/3.3)으로 도착하므로 같은 박자로 보낸다.
스키마 단계(p ≤ 0.20)에는 아직 노드가 없으므로 단계까지만 간다.

두 가지를 손봤다.
- 실은 도착 쪽만 보이게 그린다. 전 구간을 균일하게 그으면 글자 위를 가로지르는
  가느다란 줄이 되어 긁힌 자국처럼 읽혔다(모바일에서 화면을 세로로 관통했다).
- 좁은 화면에서 출발점이 그래프 띠 뒤에 있으면 보내지 않는다. 비행층(z 12)이
  띠(z 8)보다 위라, 조각이 그래프 한가운데에서 난데없이 튀어나왔다.
  출발이 보이지 않는 비행은 무엇이 무엇이 되는지 말해 주지 못한다.

층은 둘로 나눴다(`#ingFly` · `#qaFly`). 질의응답의 청소(`qaFlyClear`)가 생성 중
날아가는 조각까지 지우면 안 된다.

**손가락 탭은 click 을 기다리지 않는다.** 실기기(핸드폰 크롬 · 사파리)에서
"노드를 눌러도 반응 없음" 이 나왔다. 헤드리스에서는 합성 `click` 을 직접 보냈기
때문에 이 차이가 끝까지 드러나지 않았다. 캔버스처럼 원래 누를 수 없는 요소
위에서는 click 이 오지 않거나 늦게 오고, 탭 중에 손가락이 몇 px 만 움직여도
브라우저가 스크롤로 보고 click 을 삼킨다.

지금은 `pointerup` 에서 직접 처리한다 — 누른 자리에서 12px 안쪽이고 0.7초
안이면 탭이다. 포인터 이벤트가 없는 옛 웹킷용으로 `touchstart`/`touchend` 도
받아 두고, 방금 `pointerup` 이 처리했으면 건너뛴다. 캔버스에는
`touch-action: manipulation` 을 줘서 더블탭 확대 대기(300ms)를 없앴다.
확인: click 을 **한 번도 보내지 않고** 탭만으로 판독이 뜬다(`계산서 p.240
← hvo:sourcedFrom ZHUD30`), 끌면 뜨지 않는다.

**핸드폰에서는 프레임을 아낀다.** 484 노드 · 832 엣지를 매 프레임 다시 그리면
메인 스레드가 포화되어 고정 띠가 스크롤을 못 따라오고 탭도 늦게 처리된다 —
"스크롤해도 그래프가 안 따라옴" 의 원인으로 짚었다. `(pointer: coarse)` 일 때

- 화소 배율 상한을 2 → **1.5**. 핸드폰은 화소비 3 이 흔해서, 2 로 잘라도
  333x332 캔버스가 44만 화소다. 1.5 면 25만으로 절반 아래다.
- 프레임을 **30** 으로, 스크롤 중에는 **15** 로 내린다. 회전이 21초에 한 바퀴라
  눈에는 같고, 남는 시간이 고정 띠와 탭 처리로 간다.

커서 기기는 그대로 60 프레임 · 배율 2 다.

**진단 화면 `?debug=1`.** 주소 끝에 붙이면 왼쪽 아래에 STATE · 준비 여부 · fps ·
화면 크기 · dpr · coarse · 띠의 `position`/`top`/실제 위치 · 캔버스 화소 · 노드 수 ·
판독 상태 · 마지막 탭이 뜬다. 실기기에서만 나는 문제를 손에 들고 확인하기
위한 것이다. 평소에는 아무것도 만들지 않는다.

**같은 특이도면 나중에 쓴 것이 이긴다 — 미디어쿼리도 예외가 아니다.**
이 함정에 네 번 빠졌다. `.ing-cap` · `.ing-pipe` · `.pipe-items` · `.sg-dim em` 의
좁은 화면 손질을 기본 규칙보다 **앞에** 써 두어서 전부 없던 일이 됐다(단계가
여전히 643px, 글자가 여전히 10.5px). 그래서 좁은 화면 손질은 `style.css` 맨 끝
`좁은 화면 손질` 덩어리에 모았다. 거기에 쓰면 순서 때문에 지지 않는다.

실측으로 확인한 것 (390×844 · 360×640 · 430×932 · KO/EN):

## 배포 — GitHub Pages

이 폴더가 곧 저장소다. `git init` 과 첫 커밋은 이미 되어 있고, `.nojekyll`(Jekyll 이
`_` 로 시작하는 것을 건너뛰지 않게)과 `.gitignore`(2 MB 서체 원본 캐시 제외)도 들어 있다.

저장소는 <https://github.com/HVAC-ontoflow/HVAC-ontoflow.github.io> 이다 (조직 계정).

```bash
git remote add origin https://github.com/HVAC-ontoflow/HVAC-ontoflow.github.io.git
git push -u origin main
```

그리고 저장소 **Settings → Pages** 에서 Source 를 `Deploy from a branch`,
Branch 를 `main` / `/ (root)` 로 둔다. 1~2분 뒤 아래 주소로 열린다.

```
https://hvac-ontoflow.github.io/
```

파일명이 전부 ASCII 이므로 URL 인코딩 문제가 없고, 모든 경로가 상대경로라 하위 경로
하위 경로에 놓여도 그대로 돈다(지금은 저장소 이름이 `HVAC-ontoflow.github.io` 라 루트에 놓인다). 서버측 코드가 없어서 Pages 로 충분하다.

두 가지 주의.

- **주소는 소문자로 서빙된다.** 조직명이 `HVAC-ontoflow` 여도 Pages 주소는
  `hvac-ontoflow.github.io` 다. QR 도 소문자로 만들었다.
- **조직에는 이름이 두 개 있다.** 주소에 쓰이는 것은 login(`HVAC-ontoflow`)이고,
  프로필에 보이는 표시 이름(`skkuvac`)은 주소와 무관하다. 주소를 바꾸려면 조직
  Settings → General 에서 login 을 바꿔야 하고, 그러면 저장소 이름도
  `<새login>.github.io` 로 맞춰야 루트 주소가 유지된다.
- **저장소가 비공개면 Pages 가 안 켜진다.** 무료 플랜에서 Pages 는 공개 저장소에만
  붙는다(비공개는 Pro/Team 이 필요하다). Settings → General 맨 아래에서 Public 으로
  바꿔야 한다.

고친 뒤에는 `git add -A && git commit -m "…" && git push` 하면 자동으로 다시 배포된다.

### QR 코드


이미 만들어 두었다 — `qr/ontoflow-qr.svg` (QR 버전 4 · 33×33 모듈).

`qr/ontoflow-qr.svg`(인쇄용)와 `qr/ontoflow-qr.png`(확인용)가 나온다.
포스터에는 **SVG** 를 쓴다 — 포스터가 2385×3371 px(약 A0)로 뽑히므로 PNG 를 그만큼

오류정정은 H(30%)로 두었다. 현장에서 포스터가 접히거나 조명이 반사되고 손가락에

잘라내지 않는다.

페이지 자체는 390px 폭까지 가로 넘침 없이 세로로 쌓이므로 휴대폰 접속에 문제가 없다 —
상단 바는 좁은 화면에서 두 줄로 나뉘고, 계산식과 원문 발췌는 자기 상자 안에서만 옆으로

## 데이터 고치기

`js/data.js` 만 고치면 된다. 자주 손댈 곳은 다음 셋이다.

- `KB.equipment[].specs[].values[]` — 값 하나에 `v` · `unit` · `kind` · `status` .
  값이 둘 이상이면 배열에 그대로 넣는다. `ontology.ttl` 이 두 값을 지우지 않았으므로
  화면도 지우지 않는다. TTL 에 `3.0` 으로 적힌 값을 `3` 으로 줄이지 않으려면 `dp: 1` 을 준다.
- `KB.evidence[].steps[]` — 사슬 한 마디. `relation` 이 없으면 사슬의 머리다.
- `KB.queries[]` — CQ 한 문항. `trace` · `validation` 을 주면 해당 섹션으로 가는
  버튼이 자동으로 붙는다.

그래프는 손으로 고치지 않는다. `ontology.ttl` 이 바뀌면 다시 뽑는다.

```bash
cd 작업
python tools/extract_graph.py     # js/graph-data.js 를 덮어쓴다 (numpy 필요)
```

손댈 만한 값은 그 스크립트 안에 모여 있다 — 씨앗 장비 수(`rest[:44]`), 장비당 값 노드
개수(`picked >= 5`), 클래스별 띠 중심(`RING`), 그리고 §6 확산의 다섯 계수:

| 값 | 지금 | 뜻 |

## 레퍼런스에서 가져온 것

`레퍼런스/` 의 세 페이지(IEI 데이터센터 · Mangru · 도시공원)는 하나의 디자인 언어를
공유한다. 그 언어를 가져왔고, 색도 저쪽을 따른다. 여기에 **t-ranno**
(bistskku.com/projects/t-ranno)에서 질의응답 루프의 진행 방식을 가져왔다.

| 레퍼런스 | 가져온 것 |
| --- | --- |
| IEI 데이터센터 | 팔레트 구조(짙은 바탕 + 아주 낮은 명도의 헤어라인) · 여백으로 영역 나누기 |
| 도시공원 | 항목 등장(`--ox`/`--oy`/`--o` + 긴 감속 곡선) |
| t-ranno | 질의응답 루프 — 타이핑 → 매칭 점등 → `flyTo` 비행 → 조립 → 무한 반복 |

처음에는 흰 바탕으로 갔다 — 포스터가 흰 바탕이니 스크린샷이 그 안에 자연스럽게
앉을 것이라고 봤기 때문이다. 그런데 화면에서 보면 너무 허옇다. 그래서 IEI 가
`#07070d` 에 미색 글자를 얹는 방식 그대로, 짙은 네이비에 밝은 청백색 글자를 얹는
쪽으로 뒤집었다. 색상은 IEI 의 무채색 대신 포스터의 파랑 계열을 쓴다.

| 토큰 | 값 | 자리 |
| --- | --- | --- |
| `--bg` | `#070d18` | 페이지 바탕 |
| `--surface` | `#0b1424` | 카드 · 패널 안쪽 |
| `--panel` / `-2` / `-3` | `#101c30` / `#14233a` / `#1a2c47` | 면의 세 단계 |
| `--line` / `-2` | `rgba(160,196,238,.12)` / `.24` | 헤어라인 |
| `--text` / `--body` / `--dim` / `--dimmer` | `#e8f0fc` / `.80` / `#93accb` / `#62809f` | 글자 네 단계 |
| `--accent` / `--accent-deep` | `#5aa2ff` / `#8cc2ff` | 포인트 · 강조 |
| `--ok` / `--warn` / `--tol` | `#3ddc97` / `#fb923c` / `#38bdf8` | 검증 3색 |
| `--on-accent` | `#061020` | 포인트 색 **위에** 얹는 글자 |
| `--scrim-rgb` | `7, 13, 24` | 스크림 · 반투명 바탕의 원료 |

어두운 바탕으로 뒤집을 때 색상값만 바꿔서는 안 되는 자리가 넷 있었다.

- **"더 진한 것"의 방향이 반대다.** `--accent-deep` 은 흰 바탕에서 accent 보다
  어두웠지만(`#10437f`), 어두운 바탕에서 강조는 위로 간다(`#8cc2ff`).
- **포인트 색 위의 흰 글자.** 밝은 파랑 위에서는 흰색이 읽히지 않는다.
  `--on-accent` 토큰을 새로 두고 `#fff` 를 하드코딩한 다섯 자리를 바꿨다.
- **히어로 스크림.** 글 뒤를 눌러 주는 그라디언트가 흰색 알파였다. 색상값이
  아니라 세 숫자(`--scrim-rgb`)로 두고 그라디언트 안에서 알파만 바꿔 쓴다.
- **그래프 노드 팔레트.** 명도 순서가 뒤집힌다 — 흰 바탕에서 가장 진했던 설비가
  여기서는 가장 밝고(`#dbe9ff`), 가장 조용한 출처가 가장 어둡다(`#647c96`).
  노드를 떼어 놓는 테두리도 흰색에서 바탕색으로 바꿨다(어두운 바탕에서 흰 테두리는
  노드마다 흰 링을 만들어 오히려 지저분하다). 라벨 상자의 흰 배경도 마찬가지다.

가져온 것: 헤어라인 한 줄과 여백으로만 영역을 나누는 방식 · 크기가 아니라 명도와 아래
여백으로 위계를 만드는 작은 대문자 섹션 제목 · 숫자와 라틴 라벨은 모노, 한글은 같은
가족의 산세리프로 서체를 나누는 규칙 · `gap:1px` 헤어라인 패널 격자 · `--label` 거터
그리드 · stat tile · track+fill 막대 · chip · 두 언어를 모두 마크업에 두고 CSS 가 한쪽을
감추는 `[data-lang]` 전환 · 2~3px 모서리 · `prefers-reduced-motion` 가드 · skip link ·
상대경로 자기완결 구조.

레퍼런스는 그림자를 팝오버에만 썼다. 여기서는 한 곳 예외를 두었다 — 히어로의 미리보기
패널과 KPI 격자에 그림자를 넣었다. 뒤에 배경 그래프가 깔려 있어서, 그림자가 없으면
상자가 배경에 붙어 보이고 숫자가 뜨지 않는다. 어두운 바탕에서는 옅은 남색 그림자가
보이지 않으므로 검은 그림자(`0 2px 30px rgba(0,0,0,.45)`)로 바꾸고, 그것만으로는
경계가 서지 않아 헤어라인 한 줄을 함께 뒀다.

버린 것: 세리프 표제 · IFC 3D 뷰어 iframe · Leaflet 지도 · globe 영상 ·
그리고 포스터 §5의 **챗봇 대화 UI**.

스크롤 구동 장면 전환은 처음에 버렸다가 다시 가져왔다 — 지금은 파트 전환 전체가
스크롤에 묶여 있다("등장 연출과 파트 전환" 절).
온톨로지 그래프의 3D 도 나중에 넣었다 — 아래 "3차원" 절.

## 그래프에 관한 결정 몇 가지

- **순수 힘-지향 배치를 버렸다.** 처음에 그렇게 그렸고, 484개 노드에서는 결과가
  헤어볼이었다. 색을 어떻게 만져도 지저분했다 — 구조가 있는 데이터를 구조 없이 놓았기
  때문이다. 지금은 **반지름을 클래스가, 각도를 트리가** 정한다. 장비가 가운데(0.30R),
  출처가 테두리(0.96R)에 서고, 한 장비에 매달린 것들은 그 장비의 부채꼴 안에만 놓인다.
  덕분에 엣지 832개 중 437개가 짧은 방사선이고, 남은 현도 각도차 중앙값이 0.06 rad 다.
- **그 다음 다시 퍼뜨렸다.** 정확한 동심원은 너무 기계적으로 보인다. 그래서 클래스별
  목표 반지름을 노드마다 흔들어(표준편차 0.055R) 고리를 **두께 17~20의 띠**로 번지게
  하고, 그 상태에서 짧은 이완을 돌린다. 반발력만 키워서는 외곽이 퍼지지 않는다 — 둘레가
  길어 이웃 간격이 이미 넓고 밀어내는 힘이 반지름 방향으로 거의 작용하지 않기 때문이다
  (실측: 반발력만 올렸을 때 부품 고리의 반지름 편차가 0.9 였다). 계수는 수치로 훑어
  골랐고, 지금 값에서 최근접 이웃 거리 중앙 21.7 · 최소 11.2 · 겹침 0 이다.
  씨앗이 방사형이라 이완이 엉키지 않고 흩어지기만 한다 — 무작위에서 출발하면 헤어볼로
  수렴한다.
- **고리 안내선은 그리지 않는다.** 노드가 고리에 정확히 앉아 있을 때는 구조를 알려 주는
  선이었지만, 띠로 번진 뒤에는 노드가 선을 빗나간 것처럼 보인다. 구조는 노드의 분포가
  스스로 말한다.
- **런타임 물리 시뮬레이션을 쓰지 않는다.** 배치는 `tools/extract_graph.py` 에서 끝내고
  좌표를 굳혀 실어 보낸다. 포스터 스크린샷이 매번 같은 그림이어야 하고, 484개 노드의
  힘 계산을 휴대폰에서 매 프레임 돌릴 이유가 없다. 화면에서 움직이는 것은 바퀴 전체의
  아주 느린 회전과 노드의 미세한 숨쉬기, 그리고 등장 애니메이션뿐이다. 방사형에서 회전은
  구조를 흐트러뜨리지 않는 유일한 움직임이다 — 좌우로 흔들면 고리가 무너진다.
- **히어로 배경은 옅게, 배율은 키우지 않는다.** 확대해 보았더니(1.4배) 화면에 남는 것이
  방사선 줄무늬뿐이어서 구조가 읽히지 않았다. 전체가 들어오는 배율로 두고 중심을
  오른쪽으로 밀어, 미리보기 패널 뒤에서 반쯤 드러나게 한다. 엣지 알파 0.30 · 노드 0.88 —
  글이 위에 얹히는 자리라서 이보다 진하면 본문을 읽기 어렵다. 그림 전체는 02 탐색이 맡는다.
- **초점(focus)은 hover 와 같은 장치를 쓴다.** 질의응답에서 답이 되는 노드만
  밝힐 때, 새 그리기 경로를 만들지 않고 hover 가 쓰던 집합(`hoverNodes`·`hoverEdges`)에
  프로그램으로 값을 넣는다. 그리는 코드는 하나로 남는다. 눌린 쪽의 바닥값은
  `.05 → .09`(엣지) · `.14 → .26`(노드)로 올렸다 — 답만 밝히면 나머지가 거의
  사라져 "그래프에서 찾았다"가 아니라 "빈 화면에 몇 개 떠 있다"로 보였다.
- **외부 라이브러리를 쓰지 않는다.** D3 나 vis.js 를 CDN 에서 불러오면 그쪽이 바뀌는
  날 페이지가 같이 죽는다. `js/graph.js` 는 canvas 2D 만 쓰는 자기완결 파일이다.
- **단일출처 값 노드 2,614개는 그래프에서 뺐다.** 전부 뿌리면 그림이 아니라 안개가 된다.
  교차검증 · 불일치 · 허용오차인 값만 남겨서, 색이 곧 검증 상태를 뜻하게 했다.
- `prefers-reduced-motion` 이면 흔들림과 등장·흐름을 모두 끄고 정지 화면으로 그린다.

## 3차원

같은 그래프를 구 위에 놓은 배치를 함께 싣는다. 히어로 배경과 03 질의응답의 무대는
3D 로 돌고, 02 탐색은
`보기 2D 평면 / 3D 구체` 토글로 고른다. 주소에 `?3d` 를 붙이면 지도가 3D 로 열린다.

- **Three.js 를 쓰지 않는다.** 페이지의 외부 요청이 0건인 상태를 깨고 싶지 않았고,
  WebGL 이 막힌 PC 에서는 캔버스가 빈 화면이 된다 — 경진대회 현장에서 그건 치명적이다.
  노드마다 3차원 좌표를 미리 계산해 두고 브라우저에서는 회전 · 원근 투영 · 깊이 정렬 ·
  거리 안개만 직접 계산한다. 484개 노드는 매 프레임 투영해도 부담이 없다.
- **2D 배치의 구면 판본이다.** 2D 는 원판이었다 — 반지름은 클래스, 각도는 트리.
  3D 는 반지름을 그대로 클래스가 정하고(**동심 껍질**: HVAC 설비 185 → 부품 300 →
  값 362 → 출처 414), 트리가 정하는 것이 원 위의 각도 하나에서 **구 위의 방향**으로
  바뀐다. 설비 47대를 피보나치 구면으로 고르게 흩뿌리고, 그 아래 것들은 부모 방향
  주변의 좁은 원뿔(0.22 rad, 깊어질수록 ×0.72)에 넣는다. 설비 47대의 평균 각거리가
  0.52 rad 이므로 원뿔을 그 절반보다 작게 잡아 이웃 설비의 자식과 섞이지 않게 했다.
  그래서 3D 에서도 "한 설비에 매달린 것은 그 설비 근처에 있다"가 유지된다.
  3차원 이완 150회 뒤 최근접 이웃 거리 중앙 39.7 · 최소 21.5 · 겹침 0.
- **기본값은 2D 다.** 회전하는 구는 눈에 잘 들어오지만 구조를 읽기에는 평면이 낫다 —
  노드가 서로 겹치고 커서로 짚기도 어렵다. 그래서 읽는 화면은 2D, 3D 는 눌러서 보는
  쪽으로 두었다. 전환은 **화면 좌표를 보간**해 약 0.5초에 잇는다(3D 좌표를 보간하면
  중간 프레임이 구도 원도 아닌 모양이 된다).
- **원근을 약하게 두면 3D 로 보이지 않는다.** 처음에 카메라를 `R0*3.1` 에 두었더니
  앞뒤 크기차가 2배도 안 되어 회전하는 평면 산포처럼 읽혔다. `R0*2.4` 면 앞 1.71배 ·
  뒤 0.71배로 벌어져 부피가 보인다. 더 당기면(2.0 아래) 앞쪽 노드가 화면 밖으로
  밀려난다. 3D 는 원근 때문에 2D 보다 넓게 퍼지므로 투영에 `S3 = 0.92` 를 곱해 담는다.
- **회전 속도가 곧 깊이 단서다.** 2D 의 미세한 회전(0.0075 rad/s)처럼 두면 3D 인 줄
  모른다. 0.10 은 한 바퀴 63초로 멈춘 것처럼 보였다. 히어로 **0.30**(21초) ·
  지도 **0.24**(26초) — 배경으로 두기에 아직 조용하다.
- **깊이 안개 없이는 구가 평면 원반으로 보인다.** 뒤로 갈수록 옅게 한다
  (엣지 0.16~1.00 · 노드 0.20~1.00). 노드 크기에는 원근 배율을 곱한다.
- **3D 에서는 현을 휘지 않는다.** 휘어진 현은 평면에서 겹침을 풀어 주지만 회전하는
  3D 에서는 방향을 헷갈리게 만든다. `morph > 0.5` 부터 곧은 선으로 그린다.
- **hover 는 3D 에서도 된다.** 화면 좌표를 프레임마다 남겨 두고 그걸로 짚는다.
  겹친 노드 중에서는 **가까운 쪽**이 잡힌다.
- `prefers-reduced-motion` 이면 회전을 멈추고 고정된 각도(yaw 0.6)로 그린다.

  hover 판독은 그때도 동작한다.
- 화면에서 벗어나면 `IntersectionObserver` 로 렌더 루프를 멈춘다.
